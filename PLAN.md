# Ledgr — Rebuild Master Plan

> **This is the canonical resume file.** A fresh session should read this file first, and only this file, before touching code. It tells you exactly what's done, what decisions are already settled (don't re-litigate them), and the next concrete action.

## 0. What this project is

A personal finance app for exactly one person (the owner, email-gated via `ALLOWED_EMAIL`). Hosted on Vercel, backed by Supabase. Transactions/tags/accounts are entered **manually** — there is no bank sync, and none is planned. The core value the app needs to deliver is: fast, low-friction manual entry, and a genuinely excellent analysis section that makes sense of the data.

This plan supersedes the old `plan.md`/`stages.md` (generic AI-drafted feature lists from an earlier session, kept for history in git but no longer authoritative). The prior app was functionally reasonable but visually and conceptually basic — flat dark theme, hand-rolled conic-gradient donuts, letter-only collapsed nav icons, no motion design. This rebuild is a full design + analysis overhaul, not a bug-fix pass.

## 2. Decisions already made (do not re-litigate)

- **Backend stays Supabase, framework stays Next.js 14 (App Router) + TanStack Query.** It's already hosted, has working auth/RLS, and there's no reason to migrate infra for a single-user app. Effort goes into UI/UX and analysis depth, not backend churn.
- **Existing data is real and precious.** All schema changes are additive migrations only (new files under `supabase/migrations/`). Never edit or drop existing migrations/tables/columns.
- **Theme: refined "Liquid Glass," now with both dark and light palettes and a manual toggle.** (Revised 2026-09-03 — originally dark-only, the user asked for a light theme too.) Dark is still the default; a `ThemeToggle` in the header flips `data-theme` on `<html>` and persists to `localStorage`. No system-preference auto-switching — it's an explicit toggle, not `prefers-color-scheme`-driven. See P1.5 below for how this was retrofitted.
- **Multi-agent execution from P4 onward.** (Added 2026-09-03.) The user asked for coordinated subagents on the remaining phases instead of one linear session. Foundational/cross-cutting work (design tokens, chart primitives, theming) is done directly since it requires holding the whole design system in context; phases with low file overlap (P4 Dashboard, P5 manual entry, P6 CRUD screens) are handed to worktree-isolated agents with tight briefs pointing at this file. Whoever picks this file up next should check §7 (Agent dispatch log) for in-flight or completed agent work before starting anything new.
- **New dependencies:** `framer-motion` (motion/springs/page transitions), `lucide-react` (icon set, tree-shakeable). Charts are **hand-built SVG components** (`components/charts/*`), not a third-party chart library — full control over the glass look, no bundle bloat, no theming fights.
- **Git workflow:** commit locally after each completed phase, with a clear message. No pushes unless asked.
- **Analysis is the flagship section.** It gets built right after the shell + chart primitives exist (P3), ahead of restyling every CRUD screen.
- **App name is "Ledgr"** (single source of truth: `lib/brand.ts`'s `APP_NAME`). Revised 2026-09-03 from "Calm Ledger" — the user asked for something short, 4-5 letters, and didn't have a specific name in mind. Picked "Ledgr" (drop-vowel modern-fintech naming, keeps the "ledger" meaning). If this needs to change again, it's one constant to edit, not a repo-wide find/replace — every surface (`Sidebar`, `AppShell`, login page, `<title>`/manifest) imports from `lib/brand.ts`.

## 3. Architecture snapshot (as of rebuild kickoff)

- `app/*/page.tsx` — thin server route wrappers; real UI lives in `components/*Client.tsx`.
- Data fetching: client components use TanStack Query + `utils/supabase/client.ts`; a few server helpers remain in `lib/data.ts` (used less as pages moved to client-fetch — see `PROGRESS.md` session 25-31 history).
- Domain types: `lib/types.ts`. Finance math: `lib/finance.ts` (balances, monthly totals). Analysis/date helpers: `lib/insights.ts`.
- Offline: `lib/offline-sync.ts` + `components/SyncManager.tsx` — localStorage mutation outbox flushed when back online. Keep this working; don't regress offline quick-add.
- Auth: `middleware.ts` redirects unauthenticated users to `/login`; Supabase RLS enforces `user_id = auth.uid()` everywhere.
- Data model (`supabase/migrations/0001`–`0005`): `accounts`, `categories`, `tags` + `transaction_tags`, `transactions`, `people` + `people_ledger` (IOU tracking), `goals` + `goal_contributions`, `limits`, `recurring_rules`, `user_preferences`.

### P5 — Manual entry UX ✅
Two things, in this order, both now done in `components/TransactionsClient.tsx`, `components/QuickAdd.tsx`, `components/QuickAddModal.tsx`, `lib/offline-sync.ts`:

- [x] **Wired tags into transaction entry** (see P3's finding above — this was the priority item, not optional polish). The add/edit form in `TransactionsClient.tsx` now has a tag multi-select (toggleable chips, one per tag, colored by the tag's own `color` with a solid ring + tinted fill when active — the ring is important, see gotcha below). Create: after the transaction insert returns its real id, `transaction_tags` rows are inserted for the selected tags. Edit: opening a transaction for edit fetches its current `transaction_tags` and pre-selects those chips; saving does delete-all-then-reinsert-selection against `transaction_tags` for that transaction id (per the brief — simplest-correct at this data scale, not worth diffing). Each transaction row in the list also now shows its attached tags as small chips (a separate lightweight `transaction_tags` lookup query keyed off the visible window's transaction ids, kept independent of the main transactions query so the existing add/edit/delete/undo/optimistic-update state machine didn't need to change shape).
- [x] **Offline/outbox decision:** tag edits require a real (already-synced) transaction id. A transaction created or edited while offline still shows the full tag picker and queues normally, **except** when editing a transaction that is itself still a local-only optimistic row (`local-{uuid}` id, not yet flushed) — that specific case shows "Tags will be available once this transaction finishes syncing" and skips tag writes, since there's no real id yet to attach `transaction_tags` rows to. For every other case, tag selections **are** queued through the outbox rather than silently dropped: `lib/offline-sync.ts`'s `OfflineOutboxItem` gained an optional `tagIds` field on both `transaction-insert` and `transaction-update` items, and `flushOfflineOutbox` applies them (delete-then-insert against `transaction_tags`) once the transaction itself has synced and a real id is known — for a queued insert this means capturing the id from `.insert(...).select('id').single()`, which the flush path previously discarded. A tag-sync failure inside a flushed item is caught and logged rather than re-throwing, so it can't get an already-successfully-inserted transaction stuck retrying forever in the outbox.
- [x] Restyled `QuickAdd`/`QuickAddModal`/`TransactionsClient` onto the glass design system — `.field`/`.btn-primary`/`.btn-secondary`/`.btn-ghost`/`.data-row`/`.kicker`/`.surface-soft`, lucide icons replacing the old emoji header controls (📅🔍⌄ → `Calendar`/`Search`/`SlidersHorizontal`, with a small accent-filled badge showing the active filter count), and a framer-motion spring entrance on both modal-style overlays (`QuickAddModal`, and `TransactionsClient`'s month/search/filters popup) matching the pattern `CommandPalette` already established, instead of the plain instant-appear they had before. Every existing feature was kept working: search/filter popups, month navigation, edit/delete/undo, the offline-outbox indicator.
- [x] **Real bugs found and fixed during visual QA, not scope creep — both were silently breaking the light theme app-wide, not just in these files:**
  1. The shared `button, input, select, textarea, a { transition: background-color/border-color/color ... }` rule in `globals.css` made every themed control (every `.field` input/select, every `.btn-*`) **stuck rendering the dark theme's colors after switching to light** — confirmed via computed-style checks in both `next dev` and a production build, so not a dev-only artifact. Root cause: those properties' *specified* value is the literal, unchanging string `var(--bg-tertiary)` etc.; only the custom property's *resolved* value changes on `[data-theme]`, and Chromium doesn't restart/repaint a transition in that case — it just keeps the pre-switch used value. Fix: dropped `background-color`/`border-color`/`color` from that shared transition (and from `.data-row`'s), keeping `opacity`/`transform`/`box-shadow`. Theme switches now apply instantly instead of silently staying wrong; the lost 150ms fade was barely perceptible anyway.
  2. `.btn-danger` had a hardcoded `color: #ffd7df` (light pink) meant for dark backgrounds — illegible against light theme's pale-pink danger wash. Added a themed `--on-danger` token (`#ffd7df` dark / `#881337` light) next to the existing `--on-accent`, same pattern.
  3. The Filters-popup "Overview" stat grid used `sm:grid-cols-2 lg:grid-cols-4`, a *viewport*-width breakpoint, while actually living in the narrow half of a two-column modal layout — at a wide viewport it tried to lay out 4 columns in ~430px, causing amount text to overflow and overlap between cells. Capped that specific instance at `grid-cols-2` (the month/search variant of the same block has the full popup width and was left at 4-up).
- [x] Verified with `npx playwright install chromium` + a temporary `app/login/preview/tags-flow/` route (deleted before commit) rendering the *real* `TransactionsClient` against a small hand-written in-memory mock Supabase client (`from().select/insert/update/delete/eq/is/gte/lt/in/order/limit/single/maybeSingle`, plus the specific `transaction_tags` → `tags` join shape this feature needs) injected via a temporary, fully-reverted one-line shim in `utils/supabase/client.ts` (`if (window.__MOCK_SUPABASE_CLIENT__) return it` — gated so it only ever activates from that preview route, reverted via `git checkout` before committing, never shipped). This was necessary rather than optional: this worktree has no `.env.local`, so `createSupabaseBrowserClient()` always returns `null` here regardless of login state, meaning the tag write path could not otherwise be exercised at all, not even the "logged out" default. Confirmed end-to-end via direct inspection of the mock DB after each UI action (not just screenshots): create with 2 tags selected → both `transaction_tags` rows written against the real returned transaction id; opening an existing tagged transaction for edit → chip selection correctly pre-filled from its actual `transaction_tags` rows; changing the selection and saving → delete-then-reinsert left exactly the new set; clearing all tags and saving → `transaction_tags` rows for that transaction end up empty. Screenshotted both themes and the restyled popups after the CSS fixes above.

### P6.5 — First real-world feedback pass ✅
The user deployed and manually tested on a real phone browser after P0-P6 landed. This surfaced one significant real bug that no amount of mock-data visual QA could have caught (explained below), plus several concrete preference-driven fixes.

- [x] **Root-caused and fixed a real, high-impact bug: every route's `loading.tsx` double-nested the entire app shell.** `RouteLoading` (used by all 7 `loading.tsx` files — transactions/manage/analysis/dashboard/more/settings/calendar) wrapped itself in `<AppShell>`. That was correct pre-P1, when every page wrapped itself in its own `AppShell`. P1 moved `AppShell` into the persistent `app/(app)/layout.tsx` so the shell survives navigation — but `RouteLoading` was never updated, so from P1 onward, any time a route's data took any perceptible time to load (i.e. on every real Supabase round-trip, especially on mobile), the Suspense fallback rendered a **second, nested** sidebar/header/mobile-dock inside the first. This is exactly what the user saw as "huge empty space at the top" on Transactions/Analysis/Manage/Settings, and almost certainly a major contributor to the "immature"/laggy feeling of navigating — two overlapping sticky headers, two sets of padding, two `PageTransition` animations firing at once. Invisible in every prior visual-QA pass because those all used mock data that resolved instantly, so the loading state never actually rendered. Fixed by removing the `<AppShell>` wrap from `RouteLoading` — it now just returns the skeleton content, since the persistent layout already provides the shell. Verified by forcing an artificial multi-second delay on a test route and confirming exactly one shell renders during the wait (see `PROGRESS.md` for the repro method).
- [x] Sidebar collapse toggle: was a bare 16px chevron in a fully transparent ghost button — bumped to a 20px icon in a clearly-bounded 44px circular button (visible border + background) so it reads as an obvious tappable control, not just small.
- [x] Sidebar collapse/expand animation: the outer spacer `div` (CSS width transition, 300ms ease) and the actual floating panel (framer-motion `layout` prop *plus* a directly-set inline `style.width`) were two different, unsynchronized animation mechanisms driving what should be one movement — this is what read as janky/"immature." Now both the spacer and the panel are `motion.div`/`motion.aside` sharing one spring config (`stiffness: 300, damping: 30`), so they move in lockstep.
- [x] Renamed the app from "Calm Ledger" to **Ledgr** — user asked for something short (4-5 letters) with no specific name in mind. Centralized as `APP_NAME`/`APP_TAGLINE` in new `lib/brand.ts`, imported everywhere the name appears (`Sidebar`, `AppShell` mobile header, login page, root `<title>`/metadata, `manifest.webmanifest`, `README.md`) instead of being hardcoded per-file — a future rename is one constant, not a grep-and-replace.
- [x] Mobile performance: added a `@media (max-width: 767px)` rule that shrinks the `.ambient-field`'s blur radius and disables its drift animation. Backdrop-filter cost scales with blur radius and this is a `position: fixed`, full-viewport, continuously-animating element that every glass panel's backdrop-filter has to resample on every scroll frame — the single highest-leverage, lowest-risk thing to cut back for phone scroll smoothness without changing the desktop look.
- [x] Re-verified: build/lint clean, no console errors through sidebar collapse/expand interaction, real mobile-viewport screenshots confirm the bottom dock/FAB correctly stay pinned during actual scroll (an earlier `fullPage`-mode screenshot made them look like they overlapped content mid-page — that was a Playwright full-page-capture artifact with `position: fixed` elements, not a real bug; a normal-viewport screenshot showed it was fine).

Not changed: no evidence of a bundle-size or animation-count problem beyond the two fixes above — the double-shell bug was severe enough on its own to plausibly explain the full cluster of complaints (empty space, janky transitions, "laggy," worse on phone). If lag persists after this, the next things to instrument are actual Supabase query latency from Vercel's region and whether `export const dynamic = 'force-dynamic'` (used on most routes, forcing a fresh SSR round-trip with no caching every time) is worth relaxing for any of them — deliberately not touched here since it's a real behavior tradeoff (fresher data vs. speed), not a bug.

### P6.6 — Second real-world feedback pass ✅
More manual testing, same day. Three requests plus one thing found while investigating the first.

- [x] **"Floating sidebar" bug, real and confirmed by computed-style inspection — not just a hunch.** The sidebar was never actually `position: fixed` despite the Tailwind class being present. Root cause: `.glass-2, .glass-nav { position: relative; ... }` in `globals.css` is a plain CSS rule declared after `@tailwind utilities`, and at equal specificity a later plain-CSS rule beats an earlier utility class regardless of the HTML class order — so `.glass-nav`'s `position: relative` silently overrode Tailwind's `.fixed` on the one element that had both classes (the sidebar). This has been true since P1, not something introduced by the P6.5 animation-sync fix (that fix was checked too, and cleared — no transformed ancestor). Fixed by removing `position: relative` from that shared rule (confirmed via grep that no consumer of `.glass-2`/`.glass-nav` actually needs it). Verified with a real scroll test: `getBoundingClientRect().top` on the sidebar was identical before and after scrolling 3000px, and computed `position` reads `fixed`. Left a comment on the rule explaining the class of bug, since it's a general Tailwind gotcha (custom CSS after `@tailwind utilities` silently wins) that could recur elsewhere.
